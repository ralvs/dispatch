01 DESIGN.md's section role has no class — so it's inlined four times

This is the real gap .type-title's retirement left behind, and I missed it the first time.

What I found

DESIGN.md documents a named type role — and nothing in CSS implements it:

DESIGN.md:95–100  section:
    fontFamily: "Geist, Arial, ui-sans-serif, sans-serif"
    fontSize: "16px"
    fontWeight: 500
    lineHeight: 1.5
    letterSpacing: "-0.02em"

There is no .type-section class and no --text-section token. So every call site spells the role out by hand, using an arbitrary Tailwind value:

components/ui/section-head.tsx:18<h2 class="m-0 text-base font-medium tracking-[-0.02em] text-ink">
today/projects-card.tsx:23byte-identical to the above
today/routines-card.tsx:95byte-identical to the above
components/app-header.tsx:34same three utilities, on the wordmark link
app/globals.css:311, :319.prose-authored h2/h3 set -0.02em directly

So the retirement story is inverted from how I recorded it. .type-title (500 / -0.02em) was most of the documented section role. Pass 5 deleted it and moved its former sites to tracking-tight, which is -0.025em — away from the documented role and onto .display-tight's value. Meanwhile the role's actual value survives as an arbitrary literal in four places.

Suggestion — give the documented role a class

app/globals.css — new, next to .display-tight+ /* DESIGN.md's `section` role: a heading inside a page, where the+  * size/colour split does the hierarchy and 16px still reads as a head.+  * A class because the role is documented and was being spelled out as+  * an arbitrary `tracking-[-0.02em]` at four call sites. */+ .type-section {+   font-size: 16px;+   font-weight: 500;+   letter-spacing: -0.02em;+ }
components/ui/section-head.tsx:18 — and the three peers- <h2 className="m-0 text-base font-medium tracking-[-0.02em] text-ink">{title}</h2>+ <h2 className="m-0 type-section text-ink">{title}</h2>

Zero visual change — same three declarations, now named once. It also gives the next heading somewhere correct to land, which is exactly what was missing when three cards each invented the same literal.

A second thing worth a look

projects-card.tsx:23 and routines-card.tsx:95 render the exact h2 that SectionHead already renders. They may be able to use the component outright rather than the class. I did not verify their surrounding wrapper markup matches SectionHead's (mb-1.5 flex items-baseline justify-between gap-4), so treat this as a candidate, not a finding.

Verdict: worth fixing — 1 CSS rule + 4 one-line edits, no visual change. Open question for you: should the retired title sites (task-fields, capture-palette ×2) come back to -0.02em as type-section's tracking, or is the -0.025em they got in Pass 5 what you wanted? Right now they sit on a third value that matches neither the role nor the old class.

02 text-[15px] sits off the authored ramp

Two sites. The interesting part is that the obvious fix also removes an unexplained inconsistency.

What I found

The ramp is pinned and closed — 56 / 44 / 36 / 30 / 18 / 16 / 14 / 12 (app/globals.css:180–184). 15 is not on it. Two sites use it:

components/wordmark.tsx:18the unauth wordmark — mine, consolidated from the 3 copies Pass 5 created
components/more-menu.tsx:123pre-existing menu row label

The detail that decides it: app-header.tsx:34 renders the same wordmark at text-base — 16px. So the product name is currently set at two different sizes depending on whether you're signed in, with nothing recording why.

Suggestion — snap the wordmark to the ramp

components/wordmark.tsx:18- <span className="text-[15px] font-medium text-ink">Dispatch</span>+ <span className="type-section text-ink">Dispatch</span>  // 16px/500/-0.02em — same as app-header's wordmark, and on the ramp

This lands on point 1's new class, unifies the two wordmarks, and clears the off-ramp value in one move. The mark itself stays at size={22} vs the header's 26, which is a defensible difference — the header is chrome, the unauth page is an introduction.

This does change pixels (15 → 16 on both unauth pages), which is why I'm not doing it unasked.

Alternatives if you'd rather not:

  • Add 15 to the ramp as a real step, and update DESIGN.md.
  • Sanction it as an exception via the impeccable hook, with a recorded reason.

more-menu.tsx:123 is a separate judgement — menu rows are a different role, and 15px there may be deliberate.

Verdict: your call, because it moves pixels. My recommendation is the snap to 16 — it's the only option that removes an inconsistency instead of documenting one.

03 The -variants.ts convention for the remaining recipes

Smaller than I reported. Two of the three "hazards" have no consumers at all.

What I found

The hazard is precise: a tv() recipe re-exported through the barrel from a "use client" module. Auditing all 13 UI modules:

checkbox.tsx → checkboxclient + barrel-exported · 0 external consumers
radio.tsx → radioclient + barrel-exported · 0 external consumers
field.tsx → fieldControlclient + barrel-exported · 1 consumer, at module scope
dialog.tsxclient, has a tv(), but exports no recipe → not a hazard
badge / card / list-rowexport recipes but are server modules → safe, though only by accident
checkbox.tsx → priorityRingnot in the barrel, internal only → not a hazard

The one live consumer is the sharpest shape of the problem, because it runs at import time:

app/(authed)/tasks/task-fields.tsx:24export const CONTROL = fieldControl({ size: "md" });   ← module scope

Safe today only because task-fields.tsx is itself "use client". But a module-scope call means the throw wouldn't wait for a render — the first server module that transitively imports this file triggers it on import.

Suggestion

Given the consumer counts, I'd narrow the original recommendation rather than do all three:

  • Move fieldControl to field-variants.ts — it's the only one with a caller, and the only one already in the server-composable shape. 3 files.
  • Leave checkbox and radio. Zero consumers means zero drift; moving them now is speculative. The comment I added to the barrel already names them for whoever hits it.

The alternative — move all three for uniformity — is defensible too, and is 7 files. I lean against it only because "we moved it before anyone needed it" tends to read as noise later.

Verdict: the barrel comment probably suffices. If you want one thing done, make it fieldControl.

04 A generic TipTap suggestion factory

Confirmed at the numbers the review claimed. Real, and genuinely not a cleanup-pass job.

What I found

wikilink-suggestion.tsx (173 lines) and mention-suggestion.tsx (171 lines): 62 of 344 lines differ — 82% identical. The file itself admits it at line 8: “Cloned from wikilink-suggestion.tsx (the template).”

Everything that differs is configuration. The whole ProseMirror scaffold — React root lifecycle, destroyDropdown, renderMenu, positioning, key handling, onStart/onUpdate/onExit — is duplicated verbatim. The seven variation points:

pluginKey / namewikilinkSuggestion vs mentionSuggestion
char"[[" vs "@"
matcherdisplayTitle().includes() + self-exclusion vs normalizeName()
label accessordisplayTitle(item) vs item.name
empty copy“No matching notes” vs “No matching people”
inserted nodewikilink + sanitized label vs mention + name

Suggestion — the shape it would take

app/(authed)/notes/[id]/suggestion-extension.tsx — sketchexport function createSuggestionExtension<T extends { id: string }>(config: {
  name: string;
  char: string;
  items: T[];
  matches: (item: T, query: string) => boolean;
  label: (item: T) => string;
  emptyLabel: string;
  toNode: (item: T) => { type: string; attrs: Record<string, unknown> };
}) { /* the scaffold, once */ }
then each call site collapses to roughlycreateSuggestionExtension({
  name: "mentionSuggestion",
  char: "@",
  items: people,
  matches: (c, q) => normalizeName(c.name).includes(normalizeName(q)),
  label: (c) => c.name,
  emptyLabel: "No matching people",
  toNode: (c) => ({ type: "mention", attrs: { id: c.id, name: c.name } }),
});

Roughly 344 lines → ~120 (factory) + ~25 each. It also fixes the PluginKey collision hazard structurally, by deriving the key from name instead of relying on two comments telling each other to stay distinct.

Verdict: its own PR. This moves behaviour, not classes — React root teardown and ProseMirror key registration are the two things in this codebase most likely to fail quietly. It wants manual testing of both menus, not a rubber-stamped cleanup commit.

05 Chrome colours hardcoded in TypeScript

Small, cheap, low stakes. Included for completeness.

What I found

The two ground colours appear in CSS as the real source, and again as literals in two TS files that can't read CSS:

app/globals.css:36--bg: #fafafa — light, the source of truth
app/globals.css:111--bg: #1a1817 — dark, the source of truth
app/layout.tsx:42–43themeColor — both literals
app/manifest.ts:13–14background_color + theme_color — #fafafa twice

All four currently agree. That's five literal occurrences across two files, with no compiler link to the CSS.

Suggestion

lib/ui/chrome-colors.ts — new+ /* Mirrors --bg in app/globals.css. Static metadata exports cannot read+  * CSS custom properties, so the value is duplicated here on purpose —+  * once, rather than at each of the five call sites. */+ export const GROUND_LIGHT = "#fafafa";+ export const GROUND_DARK = "#1a1817";
app/manifest.ts- background_color: "#fafafa",- theme_color: "#fafafa",+ background_color: GROUND_LIGHT,+ theme_color: GROUND_LIGHT,

Being honest about what this doesn't fix: --bg in the CSS is still the real source, and a TS constant can drift from it just as silently as two TS constants can drift from each other. It reduces five literals to two, it doesn't close the loop. Actually closing it means generating tokens from one file, which is more machinery than this app warrants.

Verdict: low stakes — the failure mode is a stale splash screen colour, visible only after install. Worth doing if you're touching these files anyway; not worth a dedicated commit.
